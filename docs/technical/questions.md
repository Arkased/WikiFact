# Question tuning

Technical layer. The requirements are in [../requirements/questions.md](../requirements/questions.md). The design is in [../design/questions.md](../design/questions.md).

## Test plan

| Test | Requirement | Method | Pass condition |
|---|---|---|---|
| Questions | AI agents add, correct and delete facts | One labeled set per question, Q1 to Q10, about 30 inputs each at the start, and more from real use (below), each case in a group. Runs on each candidate model and effort. | Every question passes at a mean of 90 percent or more with no run under 85 percent. No question is strict. A Q1 miss writes a duplicate (F1), and the merge step repairs it on the next request in that scope. A compound (F2) is harmless to read and is rejected by Q7 at step 1 before any rewrite, and every other wrong answer is cheap to repair. This bar is the `budget` quality preset ([Quality presets](#quality-presets)): the cheapest configuration that passes is the budget choice for that question, and when none passes, the best one is the choice and is flagged. The default preset, `standard`, takes the best mean instead, because the replay showed that the budget misses add up inside the pipeline ([Quality presets](#quality-presets)). The results support other answers, and the presets make the choice the operator's. A miss is first a label review, because the sets were written without a model run. |

The prompts of October 9, 2026 come from 2 review passes over the misses, not from an optimization loop, and every change was measured on the cases that showed the miss. The sets hold 20 to 33 cases each, so a further prompt change risks a fit to the set. The rule for the next change: grow the set first, with cases from real submissions once the wiki runs, split it into a tuning half and a held-out half, and keep a change only when the held-out half does not drop. The held-out half is marked in the set file: a case with `"heldOut": true` is in it, and a case with no mark is in the tuning half. Q5 and Q7 are marked (every case with an even number); for a set whose cases carry the field, the runner prints the score of each half under the configuration line and writes it to the result entry as `halves` (`heldOut` and `tuning`, each with its case count and its mean over the runs).

**Cases from real use.** The sets grow from the real inputs of a running wiki, first `wikifact`. The worker records each question call in its call log ([Logging](deployment.md#logging)). `npm run eval:harvest -- <question> --logs <dir>` reads the call lines of one question from the call logs of a log directory, current and rolled. It drops a line whose input is the same as an earlier line or as the input of a case in the set. It takes a random sample (`--sample`, default 30; `--seed` for a repeat) and writes the sample to `eval/questions/harvest/<question>-<stamp>.json`. Each harvested case holds the input in the short form of the set files (a fact as `id`, `header`, `content`, `just`, `refs`, `deleted` and `older`, where an older version can carry `deleted`), the `ctx`, and the model's answer as `observed`, with the request id, the model, the effort and the time, so a labeler only adds `expect` and moves the case. It holds no `expect`: a label is a judgment against the rule of the question, not a copy of what the model said. A labeler writes `expect` and moves the case into the set. The labeler is a person or a model of a higher tier than the observed model; a case where the labeler is not sure goes into the set with the note "unclear", not out of it. Every case of a set is in a group, its `group` field: `designed` for a case written by hand (the value when the field is absent), `normal use` for a case built from a rebuilt wiki, and `real use` for a case from a real request of a running wiki: a harvested case, or a case built from the request row of the wiki. The runner reports the accuracy of each group of each configuration apart, next to the mean, in its output and in the result file. The pass bar applies to the whole set.

**Hard negatives.** A case can hold the optional field `kind`, 1 of `negation`, `changedValue`, `supersession` and `scopeDifference` ([Hard negatives](../design/questions.md#hard-negatives)), and the optional field `family`, a short text that is the same for the cases built from 1 pair of facts. The validator of the set files rejects any other value of `kind`. The sets of Q1 and Q4 hold at least 5 cases of each kind; the requirement test counts them. The runner prints the accuracy of each kind of each configuration under the groups, and writes it to the result entry as `kinds` (each with its case count and its mean over the runs). Each score that the runner prints (the mean, each group, each half, each kind) has a 95% Wilson interval over all answers of the runs (the case count times the run count), printed as `[low–high]` and written as `ci: [low, high]`. When a set marks `heldOut` and its cases name a `family`, the validator rejects a family with cases on both sides.

## Group question sets

The group questions Q7B and Q5B (of the first batch design) are removed, with the group sets, the sizes, the `groupSizes` key of the presets file, and `eval/questions/group-sets.ts` and `group-sizes.ts`. The loader of the presets file drops a `groupSizes` key and the entries of the removed questions (`REMOVED_QUESTION_IDS`, `src/constants.ts`), and the result reader drops the entries of the removed questions, so an older presets file and the old result files still load. `toPresetsFile` writes no entry of a removed question.

## Quality presets

The cost of a wrong answer is the operator's to weigh, so the model and effort per question come from a preset. The question sets measure accuracy and price for every question and configuration, and the summarize mode of the runner writes a summary file, `eval/questions/results/summary-<stamp>.json`. The summary file holds the measurement: the mean and cost of every pick, the pass bars, the source files and the time. A pick of a question that has 1 pooled configuration only carries `singleConfiguration: true` in the summary file, and the summarize mode prints the question names in the line of each preset, after the words "1 configuration measured for". Such a pick is the only measured configuration, not a choice among several, so measure a second configuration before the preset is used. The summarize mode also writes the tables to `config/presets.json` at the repository root. That file holds the model and effort of each question and a `source` line that names the summary file, and no measurement. It is the default model configuration. Every path in a result file is relative to the project root. The variable `WIKIFACT_PRESETS` names another file. The code holds no copy of a table, a missing file or a missing question is an error at start, and no test asserts a value in it. The summarize mode pools every run of a configuration across all result files, so a tie at 100 percent in one run is broken by the runs before it, but only runs of the current prompt: each result entry records `promptHash`, a hash of the question's system prompt, its output schema and the layout of its call, and summarize pools the entries whose hash equals the hash of the code. An entry from before the hash existed counts only for a question that has no entry with a hash yet. A prompt change therefore starts the pool of that question again, and no hand edit of a result file is needed. The summary pools `halves` (with `runs`, the runs of the entries that hold the split), `casePassRate` and `cache` over the pooled runs like the mean and `usage`; only `latency` and `stage` come from the newest entry. The line of a question prints the held-out score with its run count. The layout in the hash is whether the spec has a wiki block, which goes in the cached prefix ([the cached prefix](updates.md#call-settings)): a spec with a block adds the mark `wiki:cached-prefix` to the hashed text, and a spec with no block adds nothing, so its hash stays. A run with the block in the user message (every result file from before 2026-10-21) has another hash than a run on the cached prefix, and `summarize` pools only the second, so the 2 layouts never mix in 1 pool. The files `2026-10-21-cache-*.json` hold the hash of the new layout: the hash of their prompt and schema, recomputed with the layout mark; their numbers are as measured. Each entry also records `cache`, the cache read and write tokens of its calls (inside `usage.input`). [Cache on the new layout](#cache-on-the-new-layout) gives the accuracy and the cache tokens of the question test on the cached prefix. The measurement of October 9, 2026 showed the slope: an economy bar differed from the budget one on Q1 alone, so there is no economy preset. The table has 3 presets:

| Preset | Rule per question | Cost of one call of every question |
|---|---|---|
| `budget` | The cheapest configuration that passes the bar of [Test plan](#test-plan). When none passes, the best one, flagged. | 1.8 cents |
| `standard` | For the classification questions (Q1, Q7, Q8) and the judgment questions (Q2, Q4): the best mean, and the cheapest among ties. For the drafting questions (Q3, Q5, Q6, Q9, Q10): the budget rule. The default. | 4.8 cents |
| `premium` | The best mean, and the cheapest among ties, on every question. | 7.1 cents |

The cost column is the sum over Q1 to Q10, the questions of every preset, of `costEstimateUsd / (cases x runs)` of the pick of each question, taken from `eval/questions/results/summary-2026-10-27T18-48-53.000Z.json`.

The rule follows the cost of a wrong answer. A wrong classification or judgment writes a duplicate (F1), leaves a compound (F2) or a stale dependent, or accepts a wrong claim, and the repair waits for a later request. A wrong draft is text that is a little off, and the next correction fixes it. The kind of each question is the `kind` field of its spec in `src/updates/questions/specs/`, the one source for the runner and the summarize mode.

The replay test decided the default. On the budget table, 2 of 7 replay runs had a critical miss (a Q1 duplicate miss and a compound not split), about 12 percent of the critical cases, while the question sets showed 1 percent for Q1 alone. The pipeline gives a question more material than its test set, and the misses of Q1, Q5 and Q7 add up. A table with Sonnet on the classification and judgment questions had no critical miss in 4 runs.

`wikifact.json` has a `quality` key with one of the 3 names, default `standard`. The config loader fills `questions` from the preset at start. An entry under `questions` overrides the preset for that question. The presets file ships with the build, so a wiki never carries stale numbers in its own file, and a new measurement updates every wiki at its next start. [Open settings](README.md#open-settings), [O6](README.md#open-settings), holds the 3 tables.

### Cache on the new layout
