# Cleanup

Technical layer. The requirements are in [../requirements/cleanup.md](../requirements/cleanup.md). The design is in [../design/cleanup.md](../design/cleanup.md).

The cleanup repairs the shape of the wiki. It has 1 check: duplicate fact (F1). The cleanup runs apart from the submissions, so a submission runs no check. Code finds the candidates, one narrow question judges each one, and code writes the repair.

**When it runs.** The trigger is a write, not a clock. The finder has an interval in writes, kept in `meta.cleanup_every`, a JSON object `{ [finder]: writes }` ([O9](README.md#open-settings)). A finder with no value there starts at its seed in `CLEANUP_EVERY`:

| Finder | Seed | Base rate |
|---|---|---|
| Duplicate fact | 50 writes | Not measured in the rebuild. The test of both paths of 2026-10-20 left 3 real duplicates in 100 batch requests. |

After a run of the finder, its next interval is `nextInterval(current, repairs)` in `src/store/cleanup/limits.ts`: 0 repairs double it, `REPAIRS_TO_SHORTEN` (3) or more halve it (rounded down), 1 or 2 keep it, within `CLEANUP_EVERY_MIN` (10 writes) and `CLEANUP_EVERY_MAX` (2,000 writes). The repairs of a run are its `cleanupRepair` requests that ended with an accepted change above the `seq` of the run; a run that the cap cut counts the same way, and so does the operator's run. A run only queues its requests, so the worker counts them later: `runCleanup` adds the finders of a run to `meta.cleanup_pending` (a JSON array), and the trigger below first sets the interval of each pending finder whose `cleanupRepair` requests have all ended (none `queued` or `running`), and takes it off the list. A pending finder with a repair that has not ended stays on the list and is not due. The finder and the question stay the judges: the interval is the cost control, not a narrower finder, because a code rule leaves misses that no run sees ([Interval per check](../design/cleanup.md#interval-per-check)).

A key of `meta.cleanup_every` that names no finder is ignored. A finder with no key takes its seed, a value outside the floor and the ceiling is clamped, and a value that does not parse as an object makes the finder take its seed.

The cleanup step runs in the loop of the worker after each step that ends a request (a request of any kind, a batch, or a dropped batch with its requests 1 at a time), and after a poll that finds no queued row outside the repairs in their retry wait (below). The count of queued rows does not change it. The step: (1) it reads the ids of the queued `cleanupRepair` requests, in queue order, and runs each of them 1 time on the path of 1 request at a time (`runRequest` in `src/updates/run-once.ts`, on that row); (2) it runs the trigger below; (3) when the trigger ran a finder, it runs the requests that the finder queued, as in (1), and the trigger again, so that the finder settles in the same step. A stop, a queue pause or a rate limit ends the step at once; the requests that did not run stay `queued`, and step (1) of the next cleanup step runs them. A `cleanupRepair` request that fails an attempt follows [Queue and worker](updates.md#queue-and-worker), and the step goes on to the next one. The worker keeps, in memory, the time at which the retry wait of that request ends (`attempts * 10` seconds after the failure). Until then, steps (1) and (3) and the normal take of the loop skip it. After the wait, the first cleanup step or the first normal take that reaches it runs it; the normal take reaches it only when no other request is queued. When the normal take runs it and it fails again, the loop sleeps the retry wait, as for any request. A restart of the worker loses the wait times, so a repair can run at once after a restart. The trigger costs 1 read of `meta` and 1 `countWritesSince` query when no finder is due. It reads `meta.cleanup_seq`, a JSON object with the highest `seq` that the last run of the finder saw. When the key is absent, or its value does not parse as that object, it writes the current highest `seq` for the finder and runs nothing; a `cleanup_full` that does not parse counts as empty: a worker that starts on a wiki with an old backlog does not start it by itself, and the operator starts that run (below). A finder that is still on `cleanup_pending` is not due. Else the finder is due in 2 cases:

1. The count of writes above its `seq` in `cleanup_seq` is at least its interval in `meta.cleanup_every`. A write is a `changes` row with the outcome `accepted` of a request of the kind `submission` or `operatorEdit` (`countWritesSince`, 1 query; the children of a split submission are `submission` requests, so they count) ([Interval per check](../design/cleanup.md#interval-per-check)). A write of a `cleanupRepair` request is no write, so the cleanup does not pull its own next run closer. A split, a duplicate and a rejection are no write: the count of every `changes` row ran the checks about 2 times as often as the interval says ([research](../research/worker-throughput-2026-10-19.md)).
2. The cap cut its candidates in its last run (its name is in `meta.cleanup_full`, a JSON array), that run wrote `REPAIRS_TO_SHORTEN` (3) repairs or more, and a write (as in case 1) exists above its `seq`. `settleIntervals` counts the repairs of the run with the interval, and takes a cut finder with fewer repairs out of `cleanup_full`: it then waits for its interval.

When the finder is due, the worker writes the current highest `seq`, runs the finder, queues up to `CLEANUP_CAP` (20) `cleanupRepair` requests, and writes `cleanup_full` when the cap cut the list. Case 2 drains a backlog run after run, and it stops when the cap cuts nothing, or when the cut run wrote fewer than `REPAIRS_TO_SHORTEN` repairs. A candidate that changes again before the finder runs is examined 1 time, not 2 times. The writes under an interval wait for the next writes or for the operator cleanup. The evals call `runOnce` and never run the loop, so they never run the cleanup. An `operatorEdit` cleanup run ([Queue and worker](updates.md#queue-and-worker)) runs the finder at once, in queue order, the same way. The finder skips a candidate that a queued or running `cleanupRepair` request already holds.

A key of `meta.cleanup_seq` or a name in `meta.cleanup_full` that names no finder is ignored, and the next write of either key drops it, because the worker writes the finder `duplicateFact` only. A value that lacks the key of the finder still counts as absent.

**The finder.**

| # | Finder | Code finds | Question | Repair (code) |
|---|---|---|---|---|
| 1 | Duplicate fact (F1) | For each live fact, its `DUPLICATE_FACT_NEIGHBORS` (3) nearest live facts by `current_vec`, under `neighborDistance` of the store config. One candidate per pair, closest pair first. | Q1 | When Q1 matches the other fact of the pair: the merge of [Step 3. Merge](updates.md#step-3-merge) on the 2 facts (Q2, then Q3). |

**Duplicate fact.** Design: [Duplicate fact](../design/cleanup.md#duplicate-fact). The candidate is a pair of live fact ids, the older first. The `cleanupRepair` request loads both facts again; when one is gone or deleted, it ends `stale`. Q1 gets the newer fact as the claim (its header and content as `change`) and, as candidates, the older fact and the other nearest live facts of the newer fact, nearest first. When Q1 returns the older fact, the request runs the merge of step 3 with the 2 facts as `matches`, and the merge writes 1 change, outcome `accepted`, with the summary of the merge. When Q1 does not return it, the request writes a `cleanup_verdicts` row for the pair. The finder name is `duplicateFact`, its seed in `CLEANUP_EVERY` is 50 writes, and the Jobs page names it "Merge duplicate facts". The distance is `store.config.neighborDistance`, which `openStoreFor` takes from `highVolume.neighborDistance` of the config. The older fact of a pair is the one whose first version has the lower `seq` (the lower id on a tie). The `cleanupRepair` document is `{ finder: "duplicateFact", factIds: [older, newer] }`, and its verdict subject is the 2 ids ([Storage](storage.md#tables)). The merge writes and logs its own change (`kind: "merge"` in the `change` line), so the request does not log a second one. As on the path of a submission, the merge runs no step 7 (no Q8 or Q9): its maintenance write points each dependent of the deleted fact at the kept fact ([Step 3. Merge](updates.md#step-3-merge)). The drain of 2026-10-20 wrote about 1,700 requests through batches whose reconciliation had the cluster defect of #22, so the operator starts 1 run after the ship; the cap and `cleanup_full` drain the backlog run after run.

**A `cleanupRepair` request.** The document is `{ finder: "duplicateFact", factIds }`, a strict object. The worker runs it in queue order. A document that fails the parse ends as a `rejected` change with the reason `unsupported`, with no write and no question, on the first attempt. This is the end of a queued repair of a check that the cleanup no longer has. The requirement test "Old repair rejected" covers it. A valid request loads the candidate again: when a fact of the pair is gone or deleted, or the pair is already merged, the request finishes as `done` with no write. A repair applies through the write transaction of [Write transaction](updates.md#write-transaction) as one change with the outcome `accepted` and a summary from code. An answer that needs no change writes no `changes` row, and it writes a `cleanup_verdicts` row for the pair with the current `seq`. The finder skips a candidate while a verdict covers it, and the verdict ends when the header or the content of 1 of the 2 facts has a new version above the verdict's `seq` (`isCovered`, `src/store/cleanup/state.ts`). A model failure follows [Queue and worker](updates.md#queue-and-worker).

A `cleanupRepair` request that writes nothing, stale or with no change, ends as a `lookupRepair` with no write does: the row has the status `done` and no `error`, the process outcome is `Skipped` (no `changes` row, so the request has no `outcome`), and the worker writes one `cleanup_repair` log line at `info` with the finder, the result (`stale` or `noChange`) and the reason. A repair writes the change line of the other kinds. Each run writes one `cleanup_run` line at `info` with the finder that ran and the count of queued requests; a finder that throws writes an `error` line, and the finder waits for its next interval, or for the next write when `cleanup_full` still holds it.

## Jobs data

Design: [Operator start](../design/cleanup.md#operator-start). The Jobs page of the console reads it ([Jobs](../design/console.md#jobs)) and names the finder as a verb: "Merge duplicate facts" (`jobName` in `src/console/pages/jobs.ts`).

`jobRows(store)` in `src/store/jobs.ts` reads the state of each job on a read-only connection and writes nothing. Its result shape, its rules and the tables it reads are in [Store API reads for the signals](console.md#store-api-reads-for-the-signals): 1 row per finder, in the order of `CLEANUP_FINDERS`, with the `seq` of its last run from `meta.cleanup_seq`, the writes since, its interval from `meta.cleanup_every`, whether the cap cut its last run (`meta.cleanup_full`) and its newest `cleanupRepair` request; and the newest `reindex` request. The page links the request to the request page. "Run" queues an `operatorEdit` request ([The operatorEdit request](console.md#the-operatoredit-request)), and the console writes no table of this function.
The other fact finders (missing references, compound facts) are a future feature ([future.md](../future.md)). They fit the same run: a finder, a question, a repair, and a verdict.
