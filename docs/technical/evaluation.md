# System evaluation

Technical layer. The requirements are in [../requirements/evaluation.md](../requirements/evaluation.md). The design is in [../design/evaluation.md](../design/evaluation.md).

## Test plan

The other tests are in the technical file of their feature: the question test in [questions.md](questions.md#test-plan), the replay test in [updates.md](updates.md#tests), the relevance test and the speed test in [lookup.md](lookup.md#tests), the correction test in [submit.md](submit.md#tests), and the store tests in [storage.md](storage.md#tests).

| Test | Requirement | Method | Pass condition |
|---|---|---|---|
| Benefit | Benefit measured | `eval/benefit.ts` runs 24 repo questions and 8 repo tasks in 2 arms, with and without the wiki tools, on a copy of the dogfood wiki and the checkout of its fill commit, 10 runs each; judges each answer by terms and by a model, each task by hidden tests and by a model; reads the tokens and the dollars from the run record ([The benefit test](#the-benefit-test)). | Reported at the first runs. Then, on the "held" group: the arm with the wiki is not less often correct by a difference that counts, and costs less per question by a difference that counts (a difference counts when its 95% interval does not hold 0). |

The 5 tests of the features have one entry point, `npm run eval:all`, in `eval/all.ts`. It runs them in the order questions, relevance, replay, corrections, speed, and then the benefit test, which it skips when its flags (`--benefit "<args>"`) give neither `--db` nor `--wiki`. The speed test sits beside the questions, because it makes no model call and depends on no other test. The replay runs after the questions, because it reads the model choice that the question sets produce, and the corrections test reads the same choice for its worker. It passes the flags of each test through, runs one test alone with `--only <name>`, and writes one index file per run under `eval/results/` that points at the result files. The order and the dependencies live in that file, not in the commands a user types.

## Environments

The evals are the postdeploy tests ([Tests](../code-standard.md#8-tests)): they run against 1 deployed environment. `--env <name>` selects it from the committed list `eval/envs.json`; the default is `local`, the deployment on this computer. An entry is `{ "local": true }`, whose wiki folder comes from `deployPaths` in `scripts/lib/deploy-paths.ts` (the code that `npm run deploy` uses) with the home folder of the user; no other form exists until an eval needs one. An eval that needs a wiki takes `--wiki <name>`, the wiki of that environment (`<wikis>/<name>/game.sqlite`; the name is a plain folder name, with no separator and no `..`), or `--db <file>`, a wiki file of the test data; the two exclude each other, and `--env` without `--wiki` is an error. The bulk test, the benefit test and the speed test take these options. An eval never writes the environment: the bulk test and the benefit test copy the wiki with the SQLite backup API before they work, and the speed test (which seeds facts) is the same with a wiki of `--wiki`: it works on a copy in the temp folder of the OS. The bulk test puts its copies in `.cache/bulk-work/<env>/<wiki>/` of the repo with `--wiki` (see [the test of both paths](updates.md#high-volume-mode)); no eval puts a file into a folder of the environment, except the `-wal` and `-shm` side files that the read-only SQLite connection can make beside the wiki, with no change to the content of the wiki. The speed test with `--wiki` measures the wiki as it is: it takes no fact count (`N` with `--wiki` is an error, no synthetic facts are added), and its result file records `env`, `wiki` and `n`, the real fact count of the copy, with `reusedDatabase` false.

## The test of the reads per search

Design: [The test of the reads per search](../design/console.md#the-test-of-the-reads-per-search). `npm run eval:reads-per-search -- --db <copy.sqlite> [--out <file> | --resume <result file>]`. Code in `eval/reads-per-search.ts` and `eval/reads-per-search/`; result files in `eval/reads-per-search-results/<stamp>.json`. It works on a copy of the store, which it opens read-only.

- The searches come from `listSearchReads` (`src/store/searchReads.ts`): each search with results and minted ids, its listed facts (rank and header of the version that was the newest at the time of the search, so that the labeler sees what the agent saw), and the facts of its reads (the version read, with its full content). A listed fact with no version at that time is left out of the list and its id is noted in the `omitted` list of the search in the result file (`meta.omittedListedFacts` is the total). A read links to its search by `retrievals.ref` = `search_results.ref`, kind `read`, as `readsPerSearch` does.
- The test leaves out the searches of the 4 fill sessions of 2026-10-17 (03:36 to 05:36 UTC, as [the research](../research/no-result-searches-2026-10-19.md) does) and the searches from 2026-10-29 02:43 UTC on (`EXCLUDED` in `eval/reads-per-search/run.ts`). Those later searches are the searches of the usage tests of #2 and #98, whose prompts the test set, and of the research agents of those tests; they are not the free use of the wiki.
- 3 samples: the searches with 0, 1, and 3 or more reads, 20 each (all when fewer), drawn with the seed 1 (`sample` of `eval/lib/sample.ts`). A search with 2 reads is in no sample.
- The labeler is one model question per search through `askJudgment` (`eval/lib/judgment.ts`), the call path of the judge of the benefit test, at the `standard` setting of the judgment question Q2 (a model of a higher tier than the observed agents). It returns `found`, `not found` or `misled` and one sentence. The cost of each call comes from `config/prices.json`.
- Agreement: 0 reads agrees with `not found`, 1 read with `found`, 3 or more with `misled`. A sample passes at 80% or more, fails under it, and gives no verdict under 10 searches.
- The result file holds `meta` (the copy, the labeler model, the seed, the populations by count of reads, the cost) and, for each sample, its size, the drawn size (`size`), the count of labels done (`labeled`), the searches that agreed, the share, the verdict, and each search with its id, query, count of reads, label and reason.
- The run writes the result file after each label (through a temp file and a rename), so an error of the labeler, a Ctrl+C or a kill keeps the labels and the cost so far. `--resume <result file>` continues such a file: it labels only the searches that have no label, adds to the cost in the file and writes into the same file; it refuses a file of another seed or sample size. `--resume` and `--out` together are a usage error (exit 2), checked only by the command line: the options of the run hold one output target (a new file or the file to continue), so a run with both cannot be written.
- A file with labels missing is partial: `meta.partial` is true, a sample with missing labels (`labeled` under `size`) has the verdict `no verdict`, and `agreed` and the share count the labels so far. `meta.partial` is false when every drawn search has a label.
- The unit tests use a stub labeler and make no model call (`eval/reads-per-search/__tests__/`).

## The benefit test

Design: [The benefit test](../design/evaluation.md#the-benefit-test). Built from the spec of October 18 and 19, 2026. The differences between the spec and the code are named in the paragraphs below.

`npm run eval:benefit -- --db <copy.sqlite> --repo <path> --commit <sha> [--cases <file>] [--runs 10] [--model <id>] [--arm with|without|both] [--group held|gap|stale|all] [--limit n] [--concurrency 4]`. Code in `eval/benefit.ts` and `eval/benefit/`, in the shape of `eval/corrections/`. Result files in `eval/benefit-results/<stamp>.json`. `npm run eval:all` runs it last and skips it when `--db` is absent, because it needs the copy of a wiki and costs about (24 questions + 8 tasks) × 2 arms × 10 runs = 640 agent runs, of which the 160 task runs are long. `--kind question|task|all` runs 1 kind. An operator runs it on their own system with their own `--db` (or `--wiki` of an environment, [Environments](#environments)), `--repo` and `--cases`; the defaults are this repo and `eval/benefit.json`.

More flags: `--out <file>` names the result file (default `eval/benefit-results/<stamp>.json`); `--resume <result file>` continues an earlier run of the same commit and writes into the same file; `--verify-cases` proves the cases at the commit and runs no agent ([Proof of the cases](#proof-of-the-cases)); `--stub` runs the stub agents ([Tests of the harness](#tests-of-the-harness)); `--keep` keeps the run folder. The run folder is `.cache/benefit-work/<result file name without extension>/` in the repo, not in the OS temp folder, so `npm run clean-temp` never deletes it. A run that completes without `--keep` deletes it; a run that stops or has failed jobs keeps it, so that `--resume` finds `preloaded.sqlite` in it. At the start of each run, fresh or resumed, the test deletes the `wt/` folder of the run folder and runs `git worktree prune` on the repo, so that no worktree of a killed run is left. `--resume` refuses with a usage error (exit 2) when `meta.preload.stoppedBy` is set, `preloaded.sqlite` is missing, and the file holds at least 1 row with `copy: "preloaded"`; the error says that the preloaded copy is gone and that the run must start again. When no row has read the preloaded copy yet, `--resume` builds the preload again from round 1. `--preload-rounds <n>` sets the most rounds of [the preload](#the-benefit-test) (default 3, at least 1). `--model` defaults to the `model` of `eval/benefit/config.json` (`claude-sonnet-5-5`), for both arms. `--resume` refuses a file that differs from the run in the commit, the model, the runs, the arm, the kind, the group, the cases file or the number of cases; the head of the file is never rewritten with other values. The exit code is 0 for a complete run, 2 for a wrong command line, 3 for a run that stopped before its last job (a rate limit or a failed login) or lost a job to a fault of the machine, and 4 when `--verify-cases` finds a case that does not hold.

**Inputs.**

- `--db`: a copy of the dogfood wiki (`<wikis>/.backups/` or a copy made with the SQLite backup API). The test copies it again into its run folder with the backup API, and a run reads a copy of its own (the arm "with" copies the run folder's copy again for each run and deletes it at the end), so a run never writes into the given file and 2 runs never share a database.
- `--repo` and `--commit`: the repo that the wiki describes, and the commit at which the wiki was filled. The test checks out that commit of that repo into a worktree under the run folder (`git worktree add --detach`), and removes it at the end. The agents run with that worktree as their working directory. Git changes the worktree list of the repo one command at a time, because 2 `git worktree` commands at once can fail.
- `--cases`, default `eval/benefit.json`: the cases. A question: `{ id, kind: "question", group: "held" | "gap" | "stale", type: "locate" | "explain" | "rationale" | "behavior", complexity: "simple" | "complex", question, answer, answerContains: string[], proof: { file, line }[], staleFact?: { header, content, justification? } }`. A task: `{ id, kind: "task", taskType: "bugfix" | "feature" | "codeAndDoc", group: "held" | "stale", issue, setupPatch?: string, hiddenTests: string[], referencePatch: string, staleFact?: ... }`. The files of a task are under `<cases folder>/<cases file name without .json>/tasks/<id>/` (for `eval/benefit.json`: `eval/benefit/tasks/<id>/`): `setupPatch` and `referencePatch` name patch files in it (made by `git diff`), and `hiddenTests` lists paths in the repo, relative to its root; the test file of each path is stored as `hidden/<path>.hidden` in the task folder, with the suffix `.hidden` so that the test runner of this repo does not run it. `staleFact` is only on a "stale" case: the test writes it into the copy of that case before the runs, as an accepted change, with the justification `Stated in <first proof file> at line <line>.` so that the fact looks real (a task has no proof, so its `staleFact` carries its own `justification`). The copy with the wrong fact is made once for the case and every run of the case copies it; the other cases never see it. The enums of these fields live in `eval/lib/enums.ts`. A cases file must hold each id once, a `staleFact` on exactly the "stale" cases (with a `justification` on a task), and a `setupPatch` on each bug fix; the shipped file also keeps 1 simple and 1 complex question of each type in each group.
- A `.claude/settings.json` in the worktree with the file tools allowed (`Read`, `Grep`, `Glob`) and nothing else; a `CLAUDE.md` is not written, and the one of the repo stays as it is in that commit. The user's own settings and MCP entries are shut out with `--strict-mcp-config` and `--setting-sources project`, the slash commands and skills with `--disable-slash-commands`, and the user's memory folder with a `CLAUDE_CONFIG_DIR` of its own for each run (set when the environment holds a token or an API key, so that the login is not needed from the user's config folder). The arm "with" passes `--mcp-config` with the server of the copy on stdio (`serverSpawnCommand` of `eval/corrections/paths.ts`, 1 server per agent run, started from the source through `tsx`, never from `dist/`); the arm "without" passes an empty `--mcp-config`. `--tools` lists the built-in tools the agent sees, the same list in both arms (`Read,Grep,Glob`; for a task also `Edit,Write,Bash`).

**The preload.** Design: [A mature wiki](../design/evaluation.md#the-benefit-test). Before the measured runs, the test makes a preload copy of the run folder's copy and preloads it in rounds; `--preload-rounds <n>` sets the most rounds (default 3, at least 1; `0` is a usage error, exit 2).

1. 1 round runs each question of the groups "held" and "stale" 1 time, as an agent run of the arm "with" on the preload copy (the same command, prompt and limits as a measured run). A round writes no row and asks no judge. No stale fact is written into the preload copy.
2. After the agent runs of a round, the worker processes the queue of the preload copy until it is idle, with the same worker step and the same model transport as the service (the queue pause cleared, the operator key on).
3. The round counts the changes that the worker accepted in it (a new fact or a new version of a fact). The preload stops after a round with 0 accepted changes, or after the most rounds.

Every measured run then reads the preload copy, the gap questions and the tasks too; the copy of a "stale" case is made from the preload copy, and its `staleFact` is written into it after the preload. Each row holds `copy: "preloaded"`. The head of the file holds `meta.preload`: the most rounds, the rounds that ran, the accepted changes of each round, and `stoppedBy` (`"no change"` or `"most rounds"`). A rate limit or a failed login in a round stops the run as in a measured run. The preload copy stays in the run folder as `preloaded.sqlite`; `--resume` reuses it when `meta.preload` is complete and the file exists. When `meta.preload` is complete, the file is gone and a row read the preload copy, `--resume` refuses with a usage error. Else it makes the preload again from the start. `--resume` also refuses a file with another `--preload-rounds`. `--resume` refuses with a usage error (exit 2) a file with a row that has no `copy` or `copy: "filled"` (a file from before the preload), so that no file mixes rows of the filled wiki and of the preload copy.

**One agent run.** `claude -p --output-format stream-json --verbose --strict-mcp-config --mcp-config <file> --setting-sources project --disable-slash-commands --no-session-persistence --allowedTools <list> --tools <list> --model <id> --max-turns 12`, as the Claude consumer of the correction test, with a 5 minute limit, and the prompt on stdin (`--mcp-config` and `--allowedTools` take several values). The prompt is the question alone, with the sentence "Answer in 3 sentences at most." From the stream the test reads: the final `result`, `total_cost_usd`, `num_turns`, `usage` (input, output, cache read, cache write), the list of tool uses with the tool name and, for `search`, the query; the stream repeats a message once per content block, so a tool use counts once by its id. The SDK consumer of the correction test is not the fallback when the binary is absent: it has no file tools, so the test stops with a message that asks for the binary or for `--stub`.

**One task run.** Each task run has its own worktree of the fill commit, with `setupPatch` applied and committed as the baseline, and no `node_modules` change (`npm ci --ignore-scripts` once per worktree). The prompt is the `issue` text. The allowed tools add `Edit`, `Write` and `Bash(npm run typecheck)`, `Bash(npx vitest run *)`; `--max-turns 40`, a 20 minute limit. After the run the test reads the diff against the baseline (without `.claude/settings.json`), copies the `hiddenTests` in (a file the agent wrote at the same path is replaced), runs `npx vitest run <hiddenTests>` and `npm run typecheck`, and records `done` when both pass (`correct.tests`; the type check alone is in `correct.typecheck`). The judge then reads `{ issue, referencePatch, diff }` and gives `{ verdict, reason }`. A run that changes a file under `__tests__/` that a hidden test replaces is judged on the hidden test alone. The worktree is removed at the end.

**The judge.** 1 model question in `eval/benefit/judge.ts`, not in `src/updates/questions/`, because no worker runs it: for an answer, input `{ question, labeledAnswer, proof, answer }`; for a diff, input `{ issue, referencePatch, diff }`; output `{ verdict: "correct" | "partial" | "wrong", reason }`, on the `standard` preset model of the judgment question Q14 (read from `config/presets.json`), through the transport of the question callers (`selectTransport`, the eval rule). An invalid answer is asked again once. An empty answer is `wrong` with no model call. The terms check is `answerContains`, every term present, case-insensitive, as the correction test. Both go in the result row.

**The result file.** 1 row per (case, arm, run): `{ caseId, kind, group, type?, complexity?, taskType?, arm, run, correct: { terms?, tests?, typecheck?, judge, judgeReason? }, answer? (the final text of the agent, kept from the second run on so that a label can be reviewed without a new run), filesChanged?, usage, costUsd, turns, toolCalls: [{ tool, query? }], wallMs, error? }`, flushed after each run (written to a temporary file and renamed). The file also holds a head (`meta`: the commit, the models, the agent, the runs, the filters, the cases file, why the run stopped, the pass condition) and, after the rows, `summary` and `heldBars`. A summary per arm, per kind, per group, per kind and group, per type and per complexity (and per task type): the share right (all checks of the row pass: terms and judge for a question, hidden tests with the type check and judge for a task), the share of terms, the share done, the share the judge calls correct, the mean and the range of the dollars, of the input tokens (fresh input, cache reads and cache writes), of the output tokens and of the turns, the mean count of file reads and of wiki calls, the count of runs that ended with an error, and the delta of the arm "with" against "without" in percent. Each share right holds a 95% Wilson interval (`ci`, the helper of the question runner). The difference of the share right between the arms holds a 95% Newcombe interval (method 10, from the 2 Wilson intervals), and the difference of the mean dollars a 95% Welch interval. Each difference holds `counts`: true when its interval does not hold 0. The terminal prints the summary as a table, as `eval/corrections/report.ts` does.

**Order, stop and resume.** The jobs go through a pool of `--concurrency` runs, in the order run 1 of every case and arm, then run 2, so that a run that stops still covers every case. A rate limit or a failed login in a run or in the judge (the error text matches a 429, "rate limit", "hit your limit", "usage limit" or a failed login) stops the whole run: that run leaves no row, the jobs that follow do not start, `meta.stoppedBy` names the reason, and the exit code is 3. `--resume <file>` skips every (case, arm, run) that has a row. A job that fails for a fault of the harness or of the machine leaves no row, is listed at the end, and a resume does it again.

**Pass condition.** None at the first runs: reported. After them, on the group "held": the share correct of the arm "with" is not below the arm "without" by a difference that counts, and its mean dollars per question are below by a difference that counts. A result file with a pass condition names the bar. `heldBars` in the file and the last lines of the report give the bar per kind (questions, tasks) as `met` or `not met`, without an exit code.

### Proof of the cases

`npm run eval:benefit -- --verify-cases --commit <sha>` makes 1 worktree of the commit, installs it, and for each task: resets it, applies `setupPatch`, copies the hidden tests in, runs `npx vitest run <hiddenTests>` and `npm run typecheck`; resets it, applies the setup and the `referencePatch`, copies the hidden tests in and runs the same 2 commands. A task holds when the hidden tests fail before and pass after, and the type check passes after. For each question it checks that each `proof` file exists at the commit with at least that many lines. A task whose patch does not apply (a failed `git apply`) does not stop the proof: it is recorded as failed with the error in `error`, and the proof goes on with the next case. Only the error of `git apply` is caught: an error of any other step (the reset of the worktree, the copy of the hidden tests, a checker that cannot start) stops the proof, because it is a fault of the machine and not of the case. A hidden test checks behavior: it imports the code or runs it, and never matches the source text, so that any right fix passes. It prints one line per task with the exit codes and writes `eval/benefit-results/cases-<stamp>.json`.

### Tests of the harness

With `--stub` the agents are stubs that return the labeled answer (a question) or apply the `referencePatch` (a task) with a fixed usage that differs by arm, the judge and the checker are stubs, and `npm ci` is skipped, so the unit tests prove the arms, the result shape, the summary math, the stop and resume, the proof of the cases and the worktree cleanup with no model call (`eval/benefit/__tests__/`, with the stubs in `fakes/stub-benefit.ts`). A `--stub` run without `--db` makes a small wiki of its own. The requirement test "Benefit measured" runs the command as a process with `--stub` on a small git repo, case file and wiki.
