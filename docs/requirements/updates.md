# Process submissions

Requirements layer. The design is in [../design/updates.md](../design/updates.md).

User: none directly. The update worker does this for the consumer. The operator watches it. The roles are defined in [README.md](README.md#roles).

## Goal

Each submission makes the wiki more correct, with no person in the loop, at a known cost.

## Use cases

1. Decide the result: the claim is already in the wiki, the claim is wrong, or the claim is new or a correction.
2. Write the fact: a new fact, a correction, or a deletion. 1 fact holds 1 claim, and 1 subject has 1 fact.
3. Join 2 facts that say the same thing.
4. Check again each fact that depends on a changed fact.
5. Keep every version of every fact. Nothing is overwritten.

| Reconciliation of a batch | After the requests of a batch are written to its staging set, and before the promotion, the worker makes them consistent with each other and with the wiki: no 2 live facts in 1 scope, and no write that rests on a version of a fact that another request of the batch changed. | Stale fact deleted | The consumer sends a deletion as any other submission. The worker does not write a fact that negates it ("X no longer does Y"), so that stale facts do not build up. A claim that gives new content for the subject is a correction, and becomes a new version. | The requirement test. Eval: the question test of the judgment. | None |
| Negation on return | When a later submission sends a deleted claim again, and its observation is weaker than the reason of the deletion, the wiki does not restore the claim. It writes a new version of the deleted fact, live again, whose content says that the claim is no longer true, so that the next consumer finds the answer. The request is "accepted". An observation at least as strong as the reason of the deletion restores the claim. "Rejected" is only for a request that writes nothing. | The requirement test. Eval: the question test of the judgment and of the draft. | The replay has no case with 2 submissions in a row, so its case for a return starts from a seed that already holds the deleted fact. |
| Negation of a deleted fact | A claim that a deleted fact is no longer true agrees with the wiki: it writes nothing, and the request ends as a duplicate of the deletion, with no confirmation event. | The requirement test. | None. |

| No duplicates | A sequence of real submissions makes no duplicate fact and no fact with 2 claims. | The requirement test. Eval: the replay test, 15 cases. | 15 cases only. A failed run does not block a ship. |
| Known cost | The cost of each model question is measured for each model and effort level. | The requirement test. | None |
| Cache use | Each call of a model question reads its shared prefix from the cache when another call wrote the same prefix in the last 5 minutes. The shared prefix holds the system prompt and the subject of the wiki. ## Future

Parallel requests, a cheaper question for the judgment step, and a faster model connection, when the queue grows faster than the worker empties it.
