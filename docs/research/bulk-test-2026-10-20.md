# Bulk test of both paths, 2026-10-20

Issue #18 (high volume mode). Command: `npm run bulk-test -- --db <copy> --requests <n>`. The source is a SQLite backup of the live `wikifact` database (1,747 queued submissions at the time). Each path ran the same first n queued submissions on its own copy, one path after the other. Batch size 100, concurrency 4 (config defaults). No rate limit was hit. Result files: `eval/bulk/results/2026-10-20T23-25-50.010Z.json` (n = 10) and `eval/bulk/results/2026-10-20T23-30-53.833Z.json` (n = 100).

## Reading

- Batch is faster (5.2x at n = 10, 9.6x at n = 100) and cheaper (14x at n = 10, 25x at n = 100) at both sizes. The gap widens with n because one grouped call replaces many per-request calls and the cache write of the shared prompt is paid once per group.
- The batch path accepts fewer requests and marks more as duplicates at n = 100 (33 against 21), so it writes fewer facts. The duplicate pairs left are similar (16 against 18); neither path removes the near-duplicates that the queue itself holds.
- The outcome differences are large (27 of 100). The comparison by header undercounts agreement, since the two paths word the same claim with different headers. The reading of the 27 requests is in the section "Quality at n = 100".
- The wall times above include the time of the snapshots that the harness took after every step (reading the requests and the usage). The sequential path has about 17 times as many steps, so its time is inflated; the harness now records the time of the steps alone (`wallMs`) and the snapshot time apart (`snapshotMs`). The step logs hold no clock reading, so they do not say how large the snapshot time was. A new run is needed for the corrected times.
- The snapshot time does not change the cost. The batch path is 25 times cheaper at n = 100 with or without it.

## Quality at n = 100

The orchestrator read each of the 27 requests with another outcome. The material is the result file, its log, and the source backup, opened read-only. The working copies were removed after the run, so the fact that each path matched is inferred from the source and from the facts that each path wrote.

| Path | Pairs | Real duplicates | Partial overlaps | Not duplicates |

| Sequential | 18 | 0 | 3 | 15 |
| Batch | 16 | 3 | 1 | 12 |

Patterns:

1. The compound check of split children causes 12 of the 27 differences, in both directions. The sequential check (Q7) rejects 7 descriptions of 1 subject. The group check (Q7B) rejects 5. The check is not stable on the same text (issue #21).
2. The sequential path accepts 6 claims that live facts already hold. It also rewrites 1 exact fact into a less exact fact.
3. The batch path marks 6 claims as duplicates when they add a detail that the existing content does not hold. The detail is only in a justification, or only implied (issue #22).
4. The batch reconciliation does not match 3 new facts with the live facts that they repeat. These are the 3 real duplicates (issue #22).
5. The sequential path rejects 3 true claims with no recorded reason. In 1 of them, a false merge had deleted the related fact (issue #23).

Result: the batch path judges the requests better (14 against 9). But it leaves 3 real duplicates in 100 requests, and the sequential path leaves 0. By the bar of the requirement "High volume mode" (the same quality of result), the batch path does not pass until the reconciliation finds these duplicates.
