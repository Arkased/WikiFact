# A movable operational setup, 2026-10-27

The research of issue #86. The owner asked on 2026-10-27 for a way to move the operational setup of this project to a new project. This note lists the parts, their project values, the hidden links between them, 3 forms of a move, and 1 proposal. All facts come from the files of `build` at v0.1.98, from `~/.claude/` (read, not changed), from `gh` and from the plugin reference at `code.claude.com/docs/en/plugins-reference`.

## Result

- Of 24 parts, 4 are generic, 18 are generic with project values, and 2 are specific to WikiFact. The 18 hold specific text inside a generic frame.
- The project values are few: the owner and repo name, the board id, 3 field names with their options, 6 labels, the base branch `build`, the release branch `main`, 9 code folder names, 1 check command, and 1 name pattern for the pipe lock.
- The hard part is not the values. It is 4 links that no file states: the scripts import 5 modules of the application, the hooks run `tsx` from the project `node_modules`, the review gate matches the skill name `review`, and 3 scripts read the process table of Windows.
- A plugin cannot move the whole setup. It cannot hold `CLAUDE.md`, the permissions, or `autoMemoryEnabled` (see "Form 2").
- The proposal is a template repository with a fill script and one config file (Form 1 plus the config of Form 3). The owner chooses the form.

## 2. The hidden links

None of these links is in a README. A copy that misses one fails late or fails without a message.

1. **The scripts import the application.** `.claude/scripts/` imports `eval/lib/main.js` (`isMain`, `lowerPriorityOrThrow`; 7 files), `eval/lib/enums.js` (`BoardField`, `BoardStatus`, `IssueLabel`, `BodySection`, `BoardFixKind`, `RemoveResult`, `IssueState`; 4 files), `src/constants.js` (`ARGV_USER_OFFSET`; 4 files), `src/must.js` (`must`, `errorMessage`; 4 files) and `scripts/lib/pipe-lock.js` (`review-cap.ts`). So the folder is not self-contained. A copy of `.claude/scripts/` alone does not compile. The labels, the field names and the section names are enums of `eval/lib/enums.ts`: the project rule says that an enum is declared only there (`docs/code-standard.md`, section 1; `eslint.config.js` line 39).
2. **The hooks need the project `node_modules`.** Each hook runs `node "$CLAUDE_PROJECT_DIR/node_modules/tsx/dist/cli.mjs" <script>`. So `npm ci` must run before the first session, and `tsx` and `zod` must be dependencies. A new project with another language has no `tsx`. The task `npm ci --ignore-scripts` in the `work` skill is the same link.
3. **The review gate matches the skill name.** `review-gate.ts` acts only when `tool_input.skill === "review"`. In a plugin, the skill name is `<plugin>:review`, and the gate would never act.
4. **The review gate counts commits.** It finds the issue of a branch from the first `Refs #N` or `Fixes #N` in the commits that `build` does not hold, and it resets the count by a commit on `build` that changes `docs/`. So it needs: a branch `build`, the commit rule of the `issues` skill, and a folder `docs/`. The error "no `build` branch" allows the call, so a wrong name turns the gate off with only a line on stderr.
5. **The agent gate and the commit rule form one chain.** The gate needs `#N` in line 1 of the prompt. The agent puts `Refs #N` in its commits. The review gate reads those commits. The `work` skill step 3 states the chain. If one link changes, the cap does not count.
6. **The `work` skill names scripts, decisions and tools.** It names `.claude/scripts/board.ts` (4 times, as `node node_modules/tsx/dist/cli.mjs ...`), `npm run ship`, `npm run check -- --full`, `npm run console-shots`, 3 decision records and the issues #52 and #72, the tools `ListAgents` and `SendMessage`, the wiki MCP endpoint `/mcp`, and a link `../../../docs/decisions/0168-...md`. The `issues` skill links `../../../docs/decisions/0130-...md` and `0137-...md`. The relative links break if the skill moves out of `.claude/skills/<name>/`.
7. **The skill text states the hook texts.** `work` describes the deny text of the review gate and says "its tests check these values, not the wording". The `code-standard.md` section 6 repeats the rules of the read gate and the process cleanup in about 2,100 words. A change of a hook needs 3 edits: the script, the skill, the standard. Only the script has a test.
8. **`code-standard.md` section 6 is a spec of the hooks.** The `[script]` rules are enforced by `npm run check:standard` (`scripts/check-standard.ts`, `scripts/lib/standard.ts`). A new project must either keep that script or drop the tags.
9. **The board check and the issue templates share section names.** `board.ts` requires the sections `Context`, `Decision`, `Work`, `Outcome`, `How to review` (and `Question` for an owner question), in order. The templates in `.github/ISSUE_TEMPLATE/` and the `issues` skill must have the same names. The placeholders `Not done yet` and `Nothing to review yet` are also in code (`lib/board.ts`).
10. **The board fields are found by name, the ids are not.** `lib/board-read.ts` reads the field ids and the 4 `Status` options by name and fails when one is missing. So a new board needs the same 3 names and the same 4 options, or `enums.ts` changes. Only `PROJECT_ID`, `OWNER` and `REPO` are fixed values.
11. **The Windows process table.** `lib/processes.ts` runs `powershell Get-CimInstance Win32_Process` and `taskkill /F`. `set-priority.ts` uses the Windows priority class. `scripts/check.ts` calls `assertWindows`, listens on a named pipe `\\.\pipe\...`, and kills trees with `fkill` and `taskkill /T /F`. `clean-worktrees.ts` has a note that the delete of `node_modules` takes minutes on Windows. The project requirements say that WikiFact runs on Windows only. So items 16, 17, 22 and 23 do not run on Linux or macOS.
12. **The hooks read the internal state of Claude Code.** `lib/agents.ts` reads `~/.claude/sessions/<pid>.json` and `<session>/subagents/agent-<id>.meta.json`, and looks for the tool name `SubagentHandback` in transcripts. `set-priority.ts` waits for `~/.claude/sessions/<pid>.json`. This is not a public contract. A new version of Claude Code can break `clean-worktrees.ts` and `set-priority.ts` without a signal; the code already skips unreadable files.
13. **The read gate stands on a hook payload field.** It passes a call when `agent_id` is set. The docs of the standard say a skill with `context: fork` passes too. The `review` skill uses `context: fork` for that reason. A new skill that reads code in the main context is denied.
14. **The worktree names.** `clean-worktrees.ts` removes only `.claude/worktrees/agent-*` and the branches `worktree-agent-*`. These are names that Claude Code makes for `isolation: "worktree"`. `.gitignore`, `.prettierignore`, `vitest.config.ts`, `eslint.config.js` and `check-scope.ts` each list `.claude/worktrees/`. A new project must ignore this folder in 5 places.
15. **The scripts are part of the build of the project.** `tsconfig.json` includes `.claude/scripts`. `knip.json` lists `.claude/scripts/*.ts` as entries. `vitest.config.ts` runs `.claude/scripts/__tests__/`. `eslint.config.js` has a rule for `.claude/scripts/**/*.ts` that forces `lib/child.ts` for child processes (no console window flicker). So `npm run check` tests the setup.
16. **The permissions are not in the project.** `.claude/settings.json` holds no `permissions`. They are in `~/.claude/settings.json`: `Bash(gh *)`, `Bash(git *)`, `Bash(npm *)`, the deny of `Bash(git *worktree add*)`, `Bash(npx *)` and the `.env` paths of the project folder, and `autoMode.allow` for `gh` on the repos of `Arkased`. The user-level `mcp__wikifact` allow is also project-specific. A new project on another machine has none of these, so every `gh` call prompts.
17. **The wiki.** The `work` skill says to tell each agent to search the WikiFact wiki first and to send `requestChange`, and to check the wiki MCP endpoint after a ship. The wiki is not part of the movable setup (the owner, 2026-10-27). These sentences are project text of WikiFact, and the generic files hold none of them. An optional WikiFact module holds only the MCP interface and the setup of a dedicated wiki: the MCP server entry, the permission allow for its tools, and 1 `createWiki` call with the subject of the project. The instructions of the MCP server already tell each agent to search first and to send `requestChange`, so the module adds no rule text. The check through `/mcp` after a ship verifies the WikiFact application, so it stays in the project text of WikiFact.
18. **User-level hooks that the project assumes.** `~/.claude/hooks/` holds `deny-backslash-paths.js`, `deny-redirects.js`, `safe-compound.js`, `deny-subagent-bash-ask.js` and `block-fable-agent.cjs`. The project files do not name them, but the agent prompts rely on them.

## 3. The user-level parts

Read-only findings in `~/.claude/`:

- `CLAUDE.md`: the question format ("Questions to the owner") with `AskUserQuestion` denied in `settings.json`, the rule to prefer mechanical fixes, and the rule for the auto mode classifier. The project `CLAUDE.md` section 3 and the `work` skill step 3 point to this format by its title. It must exist in the new owner's global file, or be copied into the project `CLAUDE.md`.
- `settings.json`: `outputStyle: "ste100"`, `model: "opus"`, `permissions` (see link 16), two `PreToolUse` hook groups (Bash: path and redirect denies; `Agent|Workflow`: `block-fable-agent.cjs`), `autoMode.allow` for `gh`. It has the machine `PATH` with Git Bash, Node and the GitHub CLI.
- `settings.local.json` sets `outputStyle: "Caveman"`. It overrides `ste100`. This is a local choice and not part of the setup.
- `output-styles/ste100.md`: the style that the owner reads. Subagents also see the style, and this note follows it.
- `memory/`: the global memory files named in `~/.claude/CLAUDE.md`. The project sets `autoMemoryEnabled: false`, so a project lesson is a rule in the project files.

The new owner needs a one-time setup of these parts. They do not belong in a project repository, because they hold secrets-adjacent permissions and the user's style.

## 4. The forms

### Form 1. A template repository

A GitHub repository with the generic files in place and the project values as `{{placeholders}}` or as `TODO` lines. A new project is made with "Use this template" (or `gh repo create --template`).

- **Can move:** every file in the repo: items 1 to 20, 22, 23, the tests, the `package.json` scripts and the dev dependencies. It can hold `.claude/settings.json` with the hooks and with `autoMemoryEnabled: false`, because it is a normal file. Labels and the board fields are not copied (GitHub copies none of them), but a `scripts/setup-github.ts` in the template can create them.
- **Stays by hand:** the replacement of the values (about 30 places: `grep` finds them); the board; the user level (section 3); the permissions of the user.
- **Cost to set up:** the largest, once. The files must be cut into generic text and project text (items 2, 4, 5, 6, 8, 22). About 2 to 3 days of agent work, mainly for `code-standard.md` section 6 and for the `work` skill. The template must also compile with no application: the scripts need stand-ins for `eval/lib/main.ts`, `eval/lib/enums.ts`, `src/constants.ts`, `src/must.ts` (the link 1).
- **Cost to keep in step:** high. A template is a copy: a fix here (for example a new gate) is not in the template or in a project that already exists. Someone must port each change by hand and in both directions. A project that started from the template has no link back to it.

### Form 2. A Claude Code plugin

A directory with `.claude-plugin/plugin.json`, installed from a marketplace (a git repository) with `/plugin install`.

What a plugin can hold today (from the reference at `code.claude.com/docs/en/plugins-reference`, read on 2026-10-27):

| Component                              | In a plugin?          | Note                                                                                                                                        |
| -------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Skills (`skills/<name>/SKILL.md`)      | Yes                   | Namespaced as `<plugin>:<skill>`. This breaks link 3 (the review gate matches `review`).                                                    |
| Commands, agents, output styles        | Yes                   | The output style `ste100` could move this way.                                                                                              |
| Hooks (`hooks/hooks.json`)             | Yes                   | Use `${CLAUDE_PLUGIN_ROOT}` for the script path. Merged with the user and project hooks.                                                    |
| MCP servers, LSP servers, monitors     | Yes                   | Not needed here.                                                                                                                            |
| `settings.json` of the plugin          | Only 2 keys           | Only `agent` and `subagentStatusLine` take effect. Other keys are dropped. So `autoMemoryEnabled` and `permissions` cannot move.           |
| `CLAUDE.md`                            | No                    | A `CLAUDE.md` at the plugin root is not loaded, and `claude plugin validate` warns. Rules must go into a skill.                              |
| Issue templates, labels, board, docs   | No                    | They are files of the project repository or of GitHub.                                                                                      |
| Dependencies (`node_modules`)          | Via `${CLAUDE_PLUGIN_DATA}` | A plugin has no install step of its own. The hook command can run `npm install` into `${CLAUDE_PLUGIN_DATA}`. This is a pattern, not a feature. |
| User config                            | Yes (`userConfig`)    | Prompts for values (owner, repo, board id). The values reach hooks as `CLAUDE_PLUGIN_OPTION_<KEY>` and skills as `${user_config.KEY}` (non-secret). |
| Version and update                     | Yes                   | `version` pins the plugin. Without `version`, a git commit is the version. `/plugin update` pulls a new one.                                |

- **Can move:** items 8, 9, 10 (skills), 11 in part (hooks, but not `autoMemoryEnabled`), 12 to 19 (scripts and tests as files of the plugin, if their imports are fixed), the output style. It is the only form where a fix here reaches every project with one update.
- **Stays by hand (cannot move):** `CLAUDE.md` (item 1); `docs/` READMEs and `code-standard.md` (items 2 to 6, because the project owns them and `check:standard` reads them); `.github/ISSUE_TEMPLATE/`; the labels and the board; `autoMemoryEnabled: false`; the permissions; the scripts `ship`, `deploy`, `check`; the user level. The plugin could ship a skill `init-project` that writes these files, but then the files are a copy again (Form 3).
- **Cost to set up:** medium. The scripts must stop importing the application (link 1): copy `isMain`, `must`, `ARGV_USER_OFFSET` and the 7 enums into the plugin. The hook commands need `${CLAUDE_PLUGIN_ROOT}` and a `tsx` that does not depend on the project. The review gate must match `*:review` or `review`. The skill relative links (link 6) must change to project paths such as `docs/decisions/...`. The values come from `userConfig` or a project file. About 2 days.
- **Cost to keep in step:** low for the plugin parts (one commit and `/plugin update`), but 2 sets of files exist: the plugin here and the project files that the plugin does not hold. The plugin must work with projects that have an older `code-standard.md`. Windows-only parts (link 11) stay a limit. WikiFact itself would use the plugin too, so it removes the copy here and the check of the scripts is done in the plugin repository.
- **Risks:** the plugin API is new (fields such as `userConfig` need Claude Code v2.1.269 and later; `options` need v2.1.271); a plugin skill is shown with a prefix, so the trigger phrases of `work` (`/work`, "go") change to `/<plugin>:work`; and a hook script that runs outside the repo has no `node_modules` of the project.

### Form 3. A copy script with a config file

A script (`init-setup.ts`) and a folder of template files. The script reads `movable-setup.config.json`, copies the files into a target folder, replaces the values, creates the labels and the board with `gh`, and prints a list of manual steps. It can be run again to update (it overwrites the files that it owns and lists the files that differ).

- **Can move:** everything that Form 1 moves, plus the GitHub side: the 6 labels (`gh label create`), the board and its 2 custom fields (`gh project create`, `gh project field-create`), the fields' options, the link of the board to the repo, and the writing of the `PROJECT_ID` into the config. It can also write `.claude/settings.json` with the hooks.
- **Stays by hand:** the user level (the script can print the diff but must not change `~/.claude/`); the text that only a person can write (the requirements, the design, the principles of the project); the permissions of the user.
- **Cost to set up:** medium to high. It is Form 1 (cut the files) plus the script and its tests (about 1 more day). The cut of the files is the same work. Placeholders must have one syntax and one test that finds a placeholder left in the output.
- **Cost to keep in step:** medium. The templates live in one place (this repository or a "setup" repository), and a re-run of the script moves a change to a project. It is a one-way update with no merge: a project that edited a copied file sees its edit lost or a conflict. A manifest of file hashes (copied, edited) solves this.

### Summary of the comparison

| Criterion                    | Form 1: template repository | Form 2: plugin                         | Form 3: copy script and config      |
| ---------------------------- | --------------------------- | -------------------------------------- | ----------------------------------- |
| Moves `CLAUDE.md` and docs   | Yes, by copy                | No                                     | Yes, by copy                        |
| Moves skills and hooks       | Yes, by copy                | Yes, by install                        | Yes, by copy                        |
| Moves `autoMemoryEnabled`    | Yes (file)                  | No                                     | Yes (file)                          |
| Moves labels and the board   | No (a script can)           | No                                     | Yes (`gh`)                          |
| Moves the user level         | No                          | Output style only                      | No (prints a list)                  |
| Setup cost                   | High (2 to 3 days)          | Medium (about 2 days)                  | Medium to high (3 to 4 days)        |
| Later fix reaches a project  | By hand, both ways          | `/plugin update`, for plugin parts only | Re-run; edits can conflict          |
| Uses a new Claude Code API   | No                          | Yes                                    | No                                  |

## 5. The proposal

Use **Form 3, built on the files of Form 1**: one repository `claude-project-setup` (name for the owner to choose) that holds the generic files as templates and a script `init` that fills them from one config file and creates the GitHub side. Reasons:

- It is the only form that moves all 3 parts that a plugin cannot move (`CLAUDE.md` with the docs, the settings key `autoMemoryEnabled`, and the GitHub labels and board) and the parts that a plugin can move.
- It uses no new Claude Code API, so a version change of Claude Code cannot remove the move.
- The re-run (`init --update`) with a manifest of file hashes keeps projects in step with later changes, at the cost of one command per project. A plugin has a cheaper update, but it covers only a third of the parts.
- A plugin stays possible later for the skills and the hooks only, once the owner has 2 or more projects and wants updates without a command. The cut of the scripts (step 2) is the same work for both.

### Steps to build

1. **Make the scripts self-contained.** Move the 5 imports of link 1 into `.claude/scripts/lib/` (`isMain`, `lowerPriorityOrThrow`, `must`, `errorMessage`, `ARGV_USER_OFFSET`, the 7 enums, `pipe-lock`). Keep one definition: `scripts/` here imports them from `.claude/scripts/lib/`. Run `npm run check`. This step has value now: it removes link 1 and the code-standard rule on enums stays true with a second allowed folder.
2. **Move the project values out of the code** into `.claude/setup.config.json` (the list in section 6). `board-api.ts`, `review-cap.ts`, `clean-worktrees.ts` and `read-gate.ts` read it. A missing file or key is an error, not a default. The tests use a fixed config.
3. **Make the review gate name-proof.** Match the skill name `review` or any name that ends in `:review`, and read the name from the config.
4. **Cut the text files** into generic text and project text (items 1, 2, 4, 5, 6, 8, 9, 10). Rule: a generic file holds no `WikiFact`, no wiki tool or wiki endpoint (link 17), no issue number, no decision number. A decision number that gives a reason moves to a "Why" line in the project file. Write `code-standard.md` section 6 as a list of the hooks with one line each, and link to a file `.claude/scripts/README.md` that holds the detail (this removes the 3-edit problem of link 7).
5. **Write the template folder** `template/` with the generic files and `{{key}}` placeholders, the empty `docs/decisions/README.md` with the format, the empty layer READMEs, and the two issue templates.
6. **Write `init`** (`tsx init.ts <target> --config <file>`): check that `gh` and `git` exist; copy the files; replace the placeholders; fail if one `{{` remains; write `.claude/settings.json` with the hooks; run `git init` and the first commit on `build` and `main` if the target is empty; create the labels, the board and the 2 fields with their options; write the `PROJECT_ID`; run `npm ci --ignore-scripts` and `npm run check` in the target; print the manual steps (section 3 of this note).
7. **Add `init --update`** with `.claude/setup.manifest.json` (a SHA-256 of each copied file at copy time). A file that is unchanged in the project is replaced. A file that the project edited is written as `<name>.new` and listed.
8. **Split the Windows parts** (link 11): keep items 16, 17 and 23 as a Windows profile `platform: "win32"`. On another platform `init` does not install these hooks, and the lock in `check.ts` uses a lock file. This is a separate issue; the first version may state Windows only.
9. **Test the move on one real project.** Make a throwaway repository, run `init`, run `npm run check`, open an issue with the template, run `board.ts --fix`, start one worktree agent, and run the review twice. Then move WikiFact itself to the manifest.
10. **Record** the decision in `docs/decisions/` and the rule in `CLAUDE.md` section 4: a change to a generic file is made in the setup repository and then updated here.

Steps 1 to 3 are worth doing even if the owner picks another form.

## 7. What is not covered

- The cost numbers are estimates in days of agent work, not measurements.
- The plugin facts are from the reference page named at the top. A feature in the next release of Claude Code may change Form 2: if a plugin can hold `CLAUDE.md` rules or `permissions`, Form 2 becomes the best form.
- The user-level parts (section 3) are not moved by any form. They need a one-time page of steps for a new owner.
